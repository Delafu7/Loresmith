# OPEN_QUESTIONS.md

Conflicts between the "Full Refactor" brief and the existing codebase that I resolved by judgment call rather than blocking on. See `REFACTOR-PLAN.md` §0 for the full reality-check table this summarizes.

1. **Maps stay on the existing per-encounter `encounter_maps` schema, not a new campaign-level entity.** The brief's `/maps` + `/maps/:mapId` routes read naturally as "maps are their own top-level resource," which could imply the campaign-level Konva-canvas rewrite `REVISION-PLAN.md` §4 already scoped and explicitly deferred (calibration, undo stack, canvas library, decoupling from any one encounter). Nothing in the new brief's actual requirements (§3: coordinate labels, cell size, faction borders, size footprint, synced side panel, zoom/pan/center) needs that rewrite — all of it is buildable on the existing schema. I built the smaller version. If what you actually wanted was the deferred campaign-level map library, say so and I'll pick that up as its own phase.

2. **§8 (new interface) is scoped down, not a second full redesign.** The previous session already shipped a reviewed visual redesign (ember palette, `TurnTorch`, nav split, battle-mode layout — `REVISION-PLAN.md` §10, committed as `486cab3`). Rebuilding that from mockups again per the brief's literal "rebuild it, don't patch it" would be regressive churn. I only build/mockup the screens that genuinely don't exist yet: the landing transition, `/bestiary`, `/creature/:id`, `/maps/:mapId`. If you want the *already-shipped* screens redone under this brief's mockup-first process too, say which ones.

3. **`/campaigns/:id/session` is a rename of the existing `turns` route, not a new concept.** The existing Turns tab already becomes battle-mode automatically when an encounter is active (map + side panel, role-branched) — which is what "live session" means functionally. I renamed the route rather than building a parallel session concept.

4. **Movement-cost server-side enforcement changes existing token-drag behavior.** Today a DM can drag a token anywhere on the map with no validation (by design, informally — DMs are trusted to self-police). After §4, token moves that exceed the mover's remaining budget are rejected with `409`. This is a real behavior change for DMs specifically (not just players) — flagging it since "the DM can always override" is a common informal expectation at real tables that this enforcement doesn't special-case. If DMs should be able to bypass movement validation (a "DM override" toggle), say so; I implemented it as a hard server-side rule per the brief's explicit "cannot be exceeded, validate server-side" instruction.

5. **Creature size → cell footprint table is pending `dnd-rules` subagent confirmation**, not assumed in `REFACTOR-PLAN.md` §3 — the draft numbers there (Large=2×2, Huge=3×3, Gargantuan=4×4) are a placeholder I wrote before invoking the subagent, not a confirmed SRD table. Superseded by whatever `docs/rules/creature-sizes.md` ends up saying once that phase runs. **Resolved**: confirmed identical to the placeholder in both editions — see `docs/rules/creature-sizes.md`.

6. **Movement (§4) implementation scope, narrowed from `docs/rules/movement.md`'s full findings.** That doc surfaces real, correctly-sourced complexity beyond what I implemented:
   - **2024's occupancy passability exception for Incapacitated creatures is not implemented.** This app has no queryable "is this participant currently Incapacitated" predicate (`active_effects` stores applied conditions by name, not as structured boolean flags) — building that properly means matching effect names against a hardcoded conditions-imply-Incapacitated list, which is real but separable work. The occupancy check implemented for 2024 campaigns is: ally, Tiny, or ≥2 size categories different (omitting the Incapacitated branch). Flagged in `services/movement.ts` code comments too, not just here.
   - **The "shared distance pool, independent per-speed ceiling" semantics for switching between walk/fly/swim/burrow mid-move (§1.4) is simplified to a single numeric budget** (walk speed, doubled if dashing) with a per-cell cost multiplier when the cell's medium doesn't match one of the mover's alternate speeds, rather than tracking each speed as its own depleting pool checked against a shared total-distance-moved counter. The common case (a mover with one relevant alternate speed for the terrain they're crossing) behaves correctly; a mover switching between two *different* alternate speeds mid-path (e.g. fly then swim in the same move) may compute a stricter or looser budget than exact SRD text. Documented in `services/movement.ts`.
   - **No DM UI for painting terrain (`map_cell_overrides`) beyond a minimal click-to-cycle tool** on the map itself (normal → difficult → impassable). No dedicated "special cost" authoring UI (that field is API-only for now).
   - **2014's alternating 5/10/5 diagonal-movement variant is implemented** (as a DM-configurable `campaigns.diagonal_movement_rule` toggle, defaulting to `'flat'` per the rules doc's finding that only 2024's grounding text confirms a default at all) — but its interaction with a difficult-terrain diagonal step uses the general ×2 rule "extended" onto the alternating base cost, which `docs/rules/movement.md` §1.3 itself flags as inference, not a direct SRD citation.

   If any of these matter more than the core terrain/budget/occupancy mechanism for your table, say so and I'll pick them up as a follow-up phase.

7. **Attacks/damage (§6) — Rage-style *temporary* resistance is not implemented.** `characters.damage_resistances/vulnerabilities/immunities` (new columns) cover permanent, build-derived sources (a Dwarf's poison resistance) — `docs/rules/attacks-and-damage.md` §2.4 recommends a *separate* mechanism for temporary/conditional sources (a Barbarian's Rage resistance, which should only apply while an active "Raging" effect is present, read fresh on every damage application via a union with `active_effects`, never written into the permanent columns). That union isn't built — a raging Barbarian's resistance has to be entered into the permanent columns manually today (and manually removed when Rage ends), which is exactly the easy-to-forget-to-revert state the recommended design was meant to avoid. Flagged as a real, scoped follow-up, not silently skipped.
   - Also deferred from that same doc: `character_attacks.half_on_save` exists as a column but isn't read anywhere yet (no save-resolution flow calls it — `AttackRoller.tsx` never sends `isCritical:true` for a save-based attack, per the SRD's "saves never crit" rule, but it also doesn't yet compute "half damage on a successful save" automatically; a DM applies save-based damage today knowing whether the target's player reported a successful save, same manual judgment call as before this phase, just now with resistance/vulnerability computed for whatever number goes in).

8. **Per-campaign role verification (§7) — this codebase has no HTTP-level test harness (no supertest/equivalent), confirmed by grep.** Every existing "integration test" in this repo (including all the new ones from this refactor) calls service functions directly against a live DB, never an actual HTTP request through Express — so `requireEncounterDm`-only routes with no *service-level* authorization check of their own (faction PATCH, cell-overrides PUT/DELETE/GET, action-economy undo, token position PATCH — 17 routes total rely on this one middleware) can't be exercised by an automated test in this repo's current tooling; there's nothing at the service layer to call. I verified these by hand instead: a live two-user (DM + two players) smoke test against a running server confirmed every DM-only route correctly 403s a player (including a player acting on their *own* participant, and a second player attempting another's), and every owner-or-DM route correctly allows the owning player while rejecting a different one. The endpoints that *do* have a service-level check (`applyDamage`, `applyMonsterInstanceDamage`, `character_attacks` CRUD, `getParticipantReachableCells`) got a real automated test (`services/damageAuthz.integration.test.ts`). If durable, automated coverage of the middleware-only routes matters, the actual fix is adding `supertest` (or similar) as a dev dependency so routes can be tested end-to-end through Express — a real, if small, tooling change I didn't make unilaterally.
